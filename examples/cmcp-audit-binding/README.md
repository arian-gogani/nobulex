# Bind a Nobulex receipt to a cMCP audit entry

This offline specimen contains one `tool_call` entry generated by cMCP's
`AuditChain` at source revision
`99b80335c33789bb1d8cd575c2f3681ff82aaa1c`, followed by its session-start
entry, plus a Nobulex Ed25519 receipt that signs the cMCP entry hash, entry ID,
call ID, and session ID.

Run it from this directory. Install the package first; that resolves its
declared dependencies (`cryptography` and `rfc8785`) for you. Do not set
`PYTHONPATH` instead, because importing the package directly skips pip and
leaves those dependencies uninstalled.

```sh
python3 -m pip install ../../packages/python
python3 verify_binding.py
python3 -m unittest -v test_verify_binding.py
```

A virtualenv is recommended but not required.

The second command prints exactly this and nothing else:

```
control: PASS (BOUND_AND_VERIFIED)
mismatched call: PASS (RECEIPT_ENTRY_HASH_MISMATCH)
```

The test suite reports `Ran 5 tests` and `OK`.

Verified in a clean virtualenv on CPython 3.12.13 and on CPython 3.14.7, both
macOS, installing from a state where neither dependency was present.

The control verifies. The negative case changes the cMCP call ID and recomputes
the cMCP entry hash, making the altered entry internally consistent while
leaving the Nobulex signature unchanged. Verification rejects it because the
signed receipt is bound to the original entry hash. A separate test confirms
that editing receipt metadata without re-signing fails the pinned-key signature
check.

## What this establishes

It establishes that the included cMCP-format chain hashes consistently and
that this Nobulex receipt is signed over a reference to that exact tool-call
entry. It does not establish that cMCP produced the entry in a running gateway,
that a TEE attested it, or that the caller identity is independently known.
The fixture's public key is a demo trust anchor only. A production verifier
must obtain the authorized Nobulex key independently and verify cMCP's own
attestation or export provenance separately.
